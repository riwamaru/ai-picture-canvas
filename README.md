# AI Canvas 体験用デモ環境（Vercel + Supabase）

確定 UI（[`../index.html`](../index.html)）を、そのまま実際に動く形にしたもの。
他の人が任意の写真で試せるようにするための共有環境。

ローカルの PoC 測定システム（[`../poc`](../poc)）とは**別物**で、記録も API キーも分離してある。

---

## ⚠️ 最初に読む：なぜ PoC と分けたのか

`../poc` の `npm run studio` は、**任意画像のアップロードを意図的に受け付けない**。
[`poc/runner/studio.ts`](../poc/runner/studio.ts) の冒頭にそう書いてある（関所①隔離／PoC 実装指示書 3.2）:

> 素材はマニフェストに申告済みのものだけを扱う。ブラウザからの任意ファイルのアップロードは受け付けない。
> 受け付けると、権利区分が申告されていない画像が API へ渡る経路になる。

「他の人が任意の画像で試せる」ようにするとは、この前提を外すということである。
そこで **PoC の設計を緩めるのではなく、別環境を立てた。**

| PoC が持っていた担保 | デモ環境での代替 |
| --- | --- |
| マニフェストの `rights` 区分 | アップロード者の同意チェック（`jobs.rights_confirmed` に記録） |
| `127.0.0.1` のみ待ち受け | Supabase Auth の招待制（招待外は DB のトリガが拒否） |
| 起動時に人が `--max-images` を宣言 | `demo_limits` テーブル（設定モーダルから変更可） |
| プロセス内のカウンタ | `reserve_generation()` の行ロック（サーバーレスでも守れる） |
| `output/*/results.jsonl` | `jobs` / `job_images` テーブル（**PoC の記録には混ぜない**） |

**記録を混ぜていないことが重要である。** 混ぜると、判定基準の封印済みの母数（T-01 の 10 名）に
任意画像の試行が入り込み、`config/criteria.json` の判定が意味を失う。

## 🔻 プロバイダ構成（2026-08-16 の実測を受けて変更）

PoC の実測（[`../poc/docs/日報_2026-08-16.md`](../poc/docs/日報_2026-08-16.md)）で次が判明した：

| | OpenAI | Google |
| --- | --- | --- |
| 成功 | **0 件 / 30 件** | 35 件 |
| 拒否のされ方 | **全被写体・全強度**（`safety_violations=[sexual]`） | 写真ごと（10 名中 8 名は生成可） |

日報の見出しはそのまま「**❌ OpenAI は使えない**」「**✅ Google は仕様どおり動く**」である。
OpenAI 専用のままでは、体験環境を配っても拒否しか表示されない。

そこで **「まず OpenAI、拒否されたら Google」** の順で試す（委託者指示）。

### 確定 UI の記述との差分（要合意）

確定 UI の設定モーダルには
「障害系エラー（5xx/タイムアウト/レート制限）のみフォールバック対象で、ポリシー起因の拒否は再投入しません」
と書いてある。しかし実測では OpenAI の失敗は**全件ポリシー拒否**であり、
この規則のままだとフォールバックが一度も発動しない。

委託者判断で**ポリシー拒否もフォールバック対象**とした。根拠：

1. 禁止事項③が禁じるのは「拒否された内容を**文言を変えて**再投入すること」であり、
   同一プロンプトを別ベンダーへ送ることはこれに当たらない
2. **拒否は課金されない**（日報：拒否・非生成の 78 件は 1 円も課金されていない）ため、
   フォールバックによる追加費用が発生しない
3. OpenAI の拒否と Google の成功が**両方**記録に残るため、データはむしろ増える
   （`job_images.attempted_provider` / `attempted_error_kind`）

管理者向けシステム設定から切り替えられる（`fallback_on_policy`）。
**同じプロバイダへの再試行は行わない**（指示書 4 章のまま）。

### 除去（マスク編集）は Gemini にも回すが、方式が違う

**OpenAI と Gemini で仕組みが別物である。** 混同すると測定を誤る。

| | OpenAI | Google（Gemini） |
| --- | --- | --- |
| 方式 | `inpaint` | `semantic_mask` |
| 範囲の伝え方 | **マスク画像そのものを API へ渡す** | 輪郭を描き込んだ目印つき画像＋位置の説明文 |
| マスク外の不変 | **仕組みで担保される** | **保証なし** |
| 出力サイズ | 指定どおり | モデルが決める（元と変わる） |

Gemini にマスク画像を渡す方法は無い。対応していた `imagen-3.0-capability-001` は
2026-06-30 に停止済みで、**2026-08-28 時点のモデル一覧にも inpaint / mask 対応は 1 つも無い**
（画像モデルはすべて `generateContent` のみ）。

そこで Gemini へは元画像と「除去範囲をマゼンタの輪郭で囲んだ画像」の 2 枚を渡し、
位置と面積を文章で添え、**目印そのものは描かないよう**指示する。

**実測（2026-08-28・合成ダミー）**：目印の写り込み 0 画素、元画像との平均画素差 3.5
（PoC の目安で再圧縮ノイズ相当）。ただし出力サイズが 768×1024 → 896×1195 に変わったため、
**「マスク外が画素単位で不変」は Gemini では原理的に成立しない。**

どちらで作られたかは `job_images.edit_method` に記録し、画面にも
「マスク指定」「範囲を説明」と表示する。
**T-02 の判定基準（マスク外に変化なしが 8 割以上）は `inpaint` にしか適用できない。**
測定目的なら管理者設定の「除去も Gemini へ回す」を切り、OpenAI 単独の結果だけを見られる。

### タトゥー除去は独立したコーナーにした

確定 UI では STEP 2 のカードの 1 つだったが、**別モードとして分離**した。

- マスク画像を入力できるのは **OpenAI だけ**で、Google へフォールバックできない
- 通常加工と同じ導線に置くと「他と同じように動くはず」という誤解を生む
- 日報は「**T-02（タトゥー除去）は測定不能が確定**。実装では解決できない」としている

コーナーには**拒否される可能性が高い旨を明示**したうえで、試せるようにしてある
（拒否は課金されず、実測データとして記録される）。
除去は 1 回 1 枚・メイクを含めない（inpaint はマスク領域の中身を指示するため、
「メイクを変えろ」を混ぜると指示が破綻する）。

## 🔻 確定 UI に合わせるために PoC から意図的に変えた点（3 件）

**いずれも上長・仕様書担当と共有すべき差分である。**

### ① 自由テキスト指示欄を受け付けている

確定 UI の各カードには「自由テキスト指示」欄がある。一方 PoC 実装指示書 2 章 禁止事項②は
「安全性判定の限界を探る入力をしない」とし、PoC には自由入力の経路が実装されていない。

確定 UI が確定である以上この欄は残したが、次の歯止めを付けた：

- 200 文字で切る
- 入力全文を `jobs.free_texts` に記録し、後から監査できる
- 拒否（`policy`）された場合も記録に残り、**文言を変えた再投入は行わない**

> **判断が必要**：測定の一次データとして使うなら、自由テキストを無効化する運用も選べる。
> その場合は各カードの `free-text` 入力を `disabled` にするだけで済む。

### ② メイクにテンプレート選択を通した

PoC の `buildPrompt()` は、メイクにテンプレート ID を渡すと**例外で落ちる**設計だった
（指示内容は強度で決まるため）。確定 UI のメイクカードには
テンプレート選択（ナチュラル美肌／華やかパーティー／韓国風）と「弱・中・強 各 2 枚」が**両方**ある。

つまり確定仕様では強度とスタイルは別の軸なので、拒否をやめ、
強度の指示のあとにスタイルの指示を重ねるようにした（[`build.ts`](src/lib/vendor/prompts/build.ts) の該当箇所にコメントあり）。

### ③ テンプレートのカタログを確定 UI 側に差し替えた

PoC のカタログ（背景「スタジオ（グレー背景）」など）と確定 UI の選択肢（背景「高級ラウンジ」など）は
**別物だった**。確定 UI の選択肢に合わせて [`templates.demo.ts`](src/lib/vendor/prompts/templates.demo.ts) を新設し、
画面にはこちらだけを出している。PoC 由来の定義は [`templates.ts`](src/lib/vendor/prompts/templates.ts) にそのまま残してある。

## そのまま引き継いだもの

- **プロバイダ層** — 送信先ホストの allowlist を含めて PoC と同一
- **プロンプトの組み立て順** — v3（何を変えるか → それ以外は保つ → 本人性の保持）

- **テンプレート以外の指示文は API へ届かない**（自由テキストを除く）

## Google Drive への保存（F-06 / 仕様書 4.7）

生成した 6 枚のうち選んだ 1 枚を、**共有ドライブ**の
「店舗名 ／ キャスト名_入店年月」フォルダへ保存する。

**既定はオフ**（`demo_limits.drive_enabled = false`）。
サービスアカウントの鍵と共有ドライブの用意が済むまで、経路ごと閉じてある。

### 仕様書どおりに実装した点

| 仕様書 | 実装 |
| --- | --- |
| 4.7.1 保存先は共有ドライブに限定 | 保存前に「共有ドライブ内か」を確認できる（設定モーダルの「接続を確認する」）。マイドライブのフォルダ ID を設定していると、保存を試す前に判別して止める |
| 4.7.1 フォルダ名ではなく **ID** で解決 | `drive_folders.folder_id` が一次情報。キャストを改名しても ID は変わらないので、過去画像との紐付けが切れない |
| 4.7.2 ① 同時作成 | `folder_key` の一意制約で作成者を 1 つに絞り、作成の直前・直後に Drive を名前で検索して、重複が生まれていたら**作成時刻の古い方を残し後発をゴミ箱へ**入れる |
| 4.7.2 ② Drive 作成後に DB 保存が失敗 | Drive を叩く**前**に `drive_folder_attempts` へ試行を記録する。DB へ書けたら `settled=true`。残った行が孤児候補で、設定モーダルに一覧が出る |
| 4.7.2 ③ DB に ID があるが Drive 上で削除 | アップロード時の 404 を検知してフォルダを作り直し、DB を更新し、**Slack で管理者へ通知**する（過去画像は復旧できないため記録を残す） |
| 4.7.2 ④ Drive API の一時失敗 | `job_images.drive_status = 'failed'`（＝ Drive 未同期）として記録するだけで、**UI は止めない**。画像は Supabase Storage に残っている。1 日 1 回のバッチ（`/api/cron/drive-resync`）と、設定モーダルの「未同期を今すぐ再送する」で送り直す |

### 仕様書と違う点（2 つ）

**① 排他ロックの取り方**

仕様書 4.7.2 は「DB のアドバイザリロックまたは行ロック配下で行う」としているが、
DB のロックは 1 トランザクションの中でしか保てず、**Drive への HTTP 呼び出しをまたいでは持てない**
（Supabase の PostgREST 経由ではトランザクションを跨げない）。
そのため上表 ① のとおり、一意制約と Drive 側の検索・後始末で置き換えてある。
仕様書が「重複作成を検知した場合は先勝ちとし、後発分は削除する」と書いているのは、
まさにこの窓のための規定だと解釈した。

**② 高解像度での再生成をしていない**

仕様書 2.1 STEP 5 の確定処理は
「①選んだ 1 枚を高解像度で再生成 → ②Drive へ保存 → ③履歴へ記録」の 3 つからなる。
ここで実装したのは ② と ③ で、**① は実装していない**。
実費のかかる生成をもう 1 回走らせることになり、予約（`reserve_generation`）と
上限の設計に手を入れる必要があるため、「保存ロジック」の範囲を越える。
したがって現状 Drive へ入るのは**ドラフトと同じ 1K の画像**である。画面と設定モーダルにもそう書いてある。

### 送るもの・送らないもの

- Drive へ送るのは**画像そのもの**（保存が目的なので当然）
- **Slack へは画像も Drive の URL も送らない**。送るのは事故のときの店舗名・フォルダ名までで、
  これは既存の方針（チャンネルにいる全員が顔写真を開けてしまうのを避ける）と揃えてある
- 送信先ホストは `oauth2.googleapis.com` と `www.googleapis.com` の 2 つに固定（`src/lib/drive.ts`）。
  PoC の `vendor/providers/http.ts` には足していない（あちらは PoC と一致していることに意味があるため）

### 設定のしかた

1. Google Cloud でプロジェクトを作り、**Google Drive API を有効化**
2. サービスアカウントを作成 → キー（JSON）を作成してダウンロード
3. JSON の `client_email` と `private_key` を環境変数へ
   （`GOOGLE_DRIVE_CLIENT_EMAIL` / `GOOGLE_DRIVE_PRIVATE_KEY`）
4. Google Drive で**共有ドライブ**を作り、その中に保存用フォルダを作る
5. **共有ドライブのメンバーに `client_email` を「コンテンツ管理者」以上で追加**
   （これを忘れると権限エラーで保存できない。アドレスは設定モーダルに表示される）
6. 保存用フォルダの URL `.../folders/<ここ>` を `GOOGLE_DRIVE_ROOT_FOLDER_ID` へ
7. 自動再送用に `CRON_SECRET` を設定（未設定だとバッチは 503 を返して何もしない）
8. 設定モーダルで「接続を確認する」→ 成功したらスイッチをオンにする

> ⚠️ **共有ドライブは Google Workspace の機能**で、Business Standard 以上でないと作れない。
> 個人の Gmail アカウントや Business Starter では、この方式は使えない。
> サービスアカウントは自身のストレージ容量を持たないため、マイドライブへは保存できない（仕様書 4.1.2）。

## 上限（ブレーキ）

すべて `public.demo_limits` の 1 行で決まり、**管理者向けシステム設定から変更できる**（再デプロイ不要）。

| 項目 | 既定値 |
| --- | --- |
| 生成の受付 | 稼働中（オフで全員即停止） |
| 1 日の予算 | $12.00 |
| 1 日の枚数 | 120 枚 |
| 全体の呼び出し間隔 | 10 秒 |
| 1 人あたりの呼び出し間隔 | 60 秒 |
| 招待時の既定の枚数上限 | 24 枚（＝ 4 回ぶん） |
| 1 回の生成で作る枚数 | 6 枚 |

**1 枚あたり OpenAI 約 $0.083 / Google 約 $0.136。1 回（6 枚）で約 $0.50〜$0.82。**
予約は高いほう（Google）で押さえ、実額は生成後に差し替える。$12 でおよそ 14 回。

フォールバックしても**追加費用は発生しない**（OpenAI の拒否は課金されないため、
実費は最後に成功した 1 回ぶんだけ）。

6 枚ぶんの空きが無ければ **1 枚も作らない**。画面は弱・中・強を並べて比べるためのものなので、
「予算が尽きて 3 枚だけ出来た」状態は成果物として意味を持たない。

**失敗したときの枚数の扱い**：

| 失敗の種類 | 枚数 | コスト |
| --- | --- | --- |
| `infra`（こちら側の障害） | 返す | 返す |
| `policy`（安全性判定による拒否） | **返さない** | 返す |
| `input`（送信内容の不備） | **返さない** | 返す |

`policy` で返さないのは、禁止事項③（拒否された内容を文言を変えて再投入しない）の趣旨による。
返すと、拒否されるまで何度でも押せることになる。

**全部止めたいとき**（Supabase の SQL Editor）:

```sql
update public.demo_limits set enabled = false;
```

**検証済み。** 8 通りすべてが実際に止まることを確認してある
（全体間隔・個人間隔・個人の枚数・日次枚数・日次予算・緊急停止・招待外の拒否・未招待のサインアップ拒否）。

## Slack への生成ログ通知

**1 回の生成が終わるたびに、枚数・料金・成否・モデルを Slack へ送る**（確定 UI の設定モーダル F-10 を実動作にしたもの）。

### 送るもの・送らないもの

| | 内容 |
| --- | --- |
| **送る** | 利用者／店舗・キャスト／加工内容とテンプレート名／成功・拒否・不備・障害の内訳／モデル別の枚数とフォールバックの有無／実費（円換算つき）／所要時間／当日累計と予算消化率 |
| **送らない** | **生成画像・元画像・署名付き URL・プロンプト全文・API キー** |

> **画像と署名付き URL を送ってはならない。**
> 署名付き URL は 1 時間有効なので、チャンネルにいる全員が顔写真を開けてしまう。
> この環境は「招待された本人と管理者だけが見られる」ことを前提に権利の同意を取っている。
> Slack へ流すとその前提が崩れる。

送信内容に画像・URL・資格情報が混ざっていないことは機械的に検査済み。
キャスト名は人物を指すラベルになりうるため、設定モーダルの
「店舗名・キャスト名を本文に含める」で落とせる。

### 送信先の固定

`hooks.slack.com` への **https** 以外へは送らない（[`src/lib/slack.ts`](src/lib/slack.ts) の `isAllowedWebhook`）。
`providers/http.ts` の `ALLOWED_HOSTS` と同じ考え方で、送信先の取り違えを塞ぐ。
`https://hooks.slack.com.evil.example.com/` のような紛らわしい URL も弾くことを確認済み。

### 設定のしかた

1. Slack で App を作成 → **Incoming Webhooks** を有効化
2. **Add New Webhook to Workspace** → 通知先チャンネルを選ぶ
3. 出てきた `https://hooks.slack.com/services/…` を環境変数 `SLACK_WEBHOOK_URL` に設定

```bash
npx vercel env add SLACK_WEBHOOK_URL production
```

設定後、**管理者向けシステム設定 →「Slack への生成ログ通知」→「テスト送信する」** で疎通を確認できる
（生成を行わないので費用はかからない）。

### 届かなかったときに気づける

送信の成否は `slack_deliveries` に必ず残り、設定モーダルに直近 5 件が表示される。
**通知の失敗で生成が壊れることはない**（例外は握り、生成結果は保存される）。

未設定でも生成そのものは動く。その場合は設定モーダルに未設定である旨が出る。

## 同一条件 2 枚の作り分け（T-03 に使える）

確定 UI は候補を「弱 - パターンA / 弱 - パターンB」と見せる。この 2 枚の作り分け方は
機能仕様書 4.2.4 で**未確定**（区分 A-2）であり、PoC の T-03 で決めることになっている。

設定モーダルの「同一条件 2 枚の作り分け」で切り替えられる：

- **案 2（既定）** `micro_delta` … 表情・向き・照明に軽微な差分を付ける
- **案 1** `identical` … 同一プロンプトを 2 回実行する

seed 指定は OpenAI・Google のいずれも非対応のため、案 1 の差分はモデル固有のゆらぎのみに依存する。

## 招待のしかた

`ADMIN_EMAILS` のアドレスでログインすると、左下の「⚙️ 管理者向けシステム設定」が出る。
その中の「利用者の招待」でメールアドレスと枚数上限を入れて招待する。

**「パスワードを発行する」を推奨する。** Supabase の組み込みメール送信には厳しい回数制限がある
（独自 SMTP を設定するまでは、パスワードを発行して直接伝えるほうが確実）。

招待は 2 段構えで、片方だけでは入れない：

1. `allowed_emails` へ登録（DB のトリガが、載っていないアドレスの作成を拒否する）
2. Auth のユーザーを作成（ログイン画面は `shouldCreateUser: false` で動く）
