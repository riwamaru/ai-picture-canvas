## 2. なぜ PoC と別環境にしたか

`poc` の `npm run studio` は、**任意画像のアップロードを意図的に受け付けない**。
`runner/studio.ts` の冒頭にそう書いてある（関所①隔離／指示書 3.2）:

> 素材はマニフェストに申告済みのものだけを扱う。ブラウザからの任意ファイルのアップロードは受け付けない。
> 受け付けると、権利区分が申告されていない画像が API へ渡る経路になる。

「他の人が任意の画像で試せる」とは、この前提を外すということである。
そこで **PoC の設計を緩めるのではなく、別環境を立てた。**

| PoC が持っていた担保           | デモ環境での代替                                      |
| ------------------------------ | ----------------------------------------------------- |
| マニフェストの `rights` 区分   | アップロード者の同意チェック（記録に残す）            |
| `127.0.0.1` のみ待ち受け       | Supabase Auth の招待制（招待外は DB のトリガが拒否）  |
| 起動時に人が `--max-images` 宣言 | `demo_limits` テーブル（管理画面から変更可）        |
| プロセス内のカウンタ           | `reserve_generation()` の行ロック                     |
| `output/*/results.jsonl`       | `jobs` / `job_images`（**PoC の記録には混ぜない**）   |

**記録を混ぜていないことが重要である。** 混ぜると、判定基準の封印済みの母数（T-01 の 10 名）に
任意画像の試行が入り込み、`config/criteria.json` の判定が意味を失う。

サーバーレス（Vercel）ではプロセス内カウンタで上限を守れないため、
歯止めはすべて DB 側の行ロックへ寄せた。**8 通りすべてが実際に止まることを確認済み**
（全体間隔・個人間隔・個人の枚数・日次枚数・日次予算・緊急停止・招待外の拒否・未招待のサインアップ拒否）。

## 3. 前提が変わった：OpenAI 単独では配れない

作業の途中で、PoC の 08-16 日報の実測を確認した。

|              | OpenAI                        | Google                       |
| ------------ | ----------------------------- | ---------------------------- |
| 成功         | **0 件 / 30 件**              | 35 件                        |
| 拒否のされ方 | **全被写体・全強度**          | 写真ごと（10 名中 8 名は可） |

**OpenAI 専用のまま配ると、テスターには拒否エラーしか表示されない。**
当初 OpenAI だけを移植していたのは、この実測が出る前の優先順位（GPT Image 2 → Gemini）に
従っていたためで、前提が変わっていた。

委託者の指示により **「まず OpenAI、拒否されたら Google」** の順で試す構成にした。

### 確定 UI の記述との差分（要合意）

確定 UI の設定モーダルには
「障害系エラーのみフォールバック対象で、ポリシー起因の拒否は再投入しません」と書いてある。
しかし実測では OpenAI の失敗は**全件ポリシー拒否**であり、この規則だと一度も発動しない。

委託者判断でポリシー拒否も対象とした。根拠：

1. 禁止事項③が禁じるのは「拒否された内容を**文言を変えて**再投入すること」であり、
   同一プロンプトを別ベンダーへ送ることはこれに当たらない
2. **拒否は課金されない**（08-16 日報：拒否 78 件は 1 円も課金なし）ため追加費用が出ない
3. OpenAI の拒否と Google の成功が**両方**記録に残り、データはむしろ増える

**同じプロバイダへの再試行は実装していない**（指示書 4 章のまま）。

## 4. 確定 UI に合わせて PoC から変えた点（3 件・要合意）

確定 UI（`index.html`）の CSS・DOM 構造・文言はそのまま移植した。
そのうえで、実際に動かすために PoC の設計から 3 点変えている。

### ① 自由テキスト指示欄を通した

確定 UI の各カードには「自由テキスト指示」欄がある。一方 PoC 実装指示書 2 章 禁止事項②は
「安全性判定の限界を探る入力をしない」とし、PoC には自由入力の経路が実装されていない。

確定 UI が確定である以上この欄は残したが、200 文字で切り、入力全文を `jobs.free_texts` に
記録して監査できるようにした。**測定の一次データに使うなら無効化する運用も選べる**
（各カードの入力を `disabled` にするだけ）。

### ② メイクにテンプレート選択を通した

PoC の `buildPrompt()` はメイクにテンプレート ID を渡すと例外で落ちる設計だった。
確定 UI にはテンプレート選択と「弱・中・強 各 2 枚」が**両方**あるため、
確定仕様では強度とスタイルは別の軸と判断し、重ねるようにした。

### ③ テンプレートのカタログを確定 UI 側に差し替えた

PoC のカタログ（背景「スタジオ（グレー背景）」など）と確定 UI の選択肢（背景「高級ラウンジ」など）は
**別物だった**。確定 UI に合わせて新設し、PoC 由来の定義はそのまま残してある。

## 5. 構造の変更：1 押し 6 枚へ

初版は 1 押し 1 枚だったが、確定 UI の STEP 3 は
「弱・中・強 × 各 2 枚を非同期生成し、できたものからスロットへ反映」する設計で、
1 枚ずつでは画面が成立しない。

- `jobs` … 1 回の生成ボタン押下
- `job_images` … スロット 6 個

上限の予約も **6 枚まとめて**取る。途中で予算が尽きて「3 枚だけ出来たジョブ」を作らないため。
画面は弱・中・強を並べて比べるためのもので、半端な結果は成果物として意味を持たない。

### タトゥー除去は独立したコーナーに分けた

確定 UI では STEP 2 のカードの 1 つだったが、別モードにした。
マスク画像を入力できるのは **OpenAI だけ**で Google へフォールバックできず、
通常加工と同じ導線に置くと「他と同じように動くはず」という誤解を生むため。

08-16 日報は「**T-02 は測定不能が確定**。実装では解決できない」としている。
コーナーには**拒否される可能性が高い旨を明示**したうえで試せるようにした。
除去は 1 回 1 枚・メイクを含めない（inpaint はマスク領域の中身を指示するため、
「メイクを変えろ」を混ぜると指示が破綻する）。

## 6. Slack への生成ログ通知（委託者指示）

1 回の生成が終わるたびに、枚数・料金・成否・モデル・当日累計を Slack へ送る。

| 送る | 利用者／店舗・キャスト／加工内容とテンプレート名／成功・拒否・不備・障害の内訳／モデル別の枚数とフォールバックの有無／実費（円換算つき）／所要時間／当日累計と予算消化率 |
| ---- | ---- |
| **送らない** | **生成画像・元画像・署名付き URL・プロンプト全文・API キー** |

**画像と署名付き URL は送らない。** 署名付き URL は 1 時間有効なので、
送るとチャンネルにいる全員が顔写真を開けてしまう。この環境は
「招待された本人と管理者だけが見られる」ことを前提に権利の同意を取っており、
Slack へ流すとその前提が崩れる。混入がないことは機械的に検査した。

送信先は `hooks.slack.com` への https に固定（`providers/http.ts` の allowlist と同じ考え方）。
`https://hooks.slack.com.evil.example.com/` のような紛らわしい URL も弾く。

キャスト名は人物を指すラベルになりうるため、設定で落とせるようにした。

## 7. 直した不具合（5 件）

いずれも移植・実装の途中で見つけたもの。

| #   | 症状                                                     | 原因                                                                       |
| --- | -------------------------------------------------------- | -------------------------------------------------------------------------- |
| 1   | STEP 1 のプレビュー画像が 0×0 で見えない                | `.preview-wrap` は CSS で `display:none`。モックは JS が実行時に block にしていた |
| 2   | 塗ったマスクが他を操作すると毎回消える                   | 除去パネルを関数コンポーネントとして内側で定義し、再描画のたびに再マウントされていた |
| 3   | 枚数設定によらず「弱・中・強 各 2 枚」と表示             | 文言のハードコード                                                         |
| 4   | フォールバックの理由を常に「拒否」と表示                 | 障害（infra）と拒否（policy）を書き分けていなかった                        |
| 5   | **Slack へ送れているのに「送信できませんでした」と表示** | ダミー UUID が外部キーに弾かれ、その挿入エラーを握り潰していた             |

5 番は原因が 2 つ重なっていた。テスト送信が実在しない `jobId` を渡していたこと（外部キー違反）と、
`post()` が insert の戻り値を見ていなかったこと。結果、送信は成功しているのに記録が残らず、
「最後の記録を読んで成否を返す」作りが「記録なし＝失敗」と誤報告していた。
**DB を読み戻さず送信結果そのものを返す**ように直した。

## 8. 私の判断の訂正（2 件）

### ① Gemini の必要性を最初に伝えていなかった

「gemini api key は貼らない？」と指摘を受けるまで、デモが OpenAI 専用であることも、
そのままでは拒否しか見えない可能性が高いことも説明していなかった。
指摘がなければ、拒否しか出ない環境を配るところだった。

### ② メール送信の副作用を確かめずに実行した

Redirect URLs の設定を検証する際、「許可されていない URL は拒否されるはず」と考えて
不正な URL で送信を試した。実際には **Supabase は拒否せず Site URL に差し替える**挙動で、
検証として無意味だったうえ、**限りあるメール送信を 1 通消費し、
リンク先の誤ったメールを委託者へ送ってしまった**。
送信の副作用がある操作を、挙動を確かめずに実行したのが誤り。
